# 0.2.11-rc.16

构建时间：2026-11-12 09:10:34 +08:00
产物：`DeepSeek-Harness-Frozen-Setup-0.2.11-rc.16.exe`（483.6 MiB / 507,083,739 B）
SHA-256：`D36D55F89D37C5DE3DCF7EA92BF39037AE936623A3B81AF09C3A8CE86E6B467B`

本版修一个「用过一段时间后必然启动失败」的问题：桌面版某天起固定报
「应用无法启动或已意外停止 · desktop welcome: Web authentication failed」，
重启、禁用插件、重装都无效。根因是认证 cookie 累积撑爆请求头；修复方式是启动前自动清理。

## 1. 现象与根因

- 现象：`%APPDATA%\@deepseek-ai\dsh-desktop\logs\crash-<时间>-host.log` 里只有
  `desktop welcome: Web authentication failed`，宿主没有别的异常；手动清空
  `%APPDATA%\@deepseek-ai\dsh-desktop\Network\Cookies` 后立刻恢复。
- 机制：桌面壳每次启动都用随机端口起宿主（`dsh web --port 0`），Web 认证 cookie 的
  名字按「主机:端口」哈希生成（`dsh-auth-<sha256(authority)>`），有效期 30 天；
  Chromium 对 `127.0.0.1` **不区分端口**地保存，并在每次请求里全量发送
  （netlog 事件为 `INCLUDE, WARN_PORT_MISMATCH`）。于是每启动一次就多一个 cookie，从不回收。
- 临界点：Cookie 请求头 + 常规浏览器头超过 Node http 的请求头解析上限（约 16KB）后，
  宿主对所有请求直接回 `431 Request Header Fields Too Large`；外壳的 welcome 流程
  （`connectDesktopWelcome`）把任何非 2xx 当成认证失败，弹出「应用无法启动」。
- 复现证据：本机故障时 cookie 库里有 **71 个** `dsh-auth-*`，拼出的 Cookie 头
  **16,186 字节**。用同版本宿主实测：16,186 B cookie + 常规浏览器头 → **431**；
  仅 cookie → 401；15,000 B + 常规头 → 401。边界与推断一致。

## 2. 修复

- 新增 `tools/prune-stale-dsh-cookies.mjs`（源文件 `frozen-build-src/prune-stale-dsh-cookies.mjs`）：
  用 Node 内置 `node:sqlite` 打开 Electron 的 cookie 库，只删除 `host_key='127.0.0.1'`
  且名字以 `dsh-auth-` 开头的行；改前在同目录留 `Cookies.bak-<时间戳>` 备份。
  应用正在运行（库被锁）时直接报错退出；支持 `--dry-run` 与 `--db <路径>`。
- `Launch.ps1`（标记 `dsh:auth-cookie-prune`）：启动宿主前用随包 node.exe 跑一次上述清理，
  成功 / 跳过 / 失败都只写一行启动日志（`%TEMP%\dsh-frozen-launch-*.log`），绝不阻断启动；
  应用已在运行时数据库被锁，脚本自动跳过，不会破坏正在使用的会话。
- `Build-FrozenSetup.ps1`：把新脚本随 `tools\` 一起同步进 payload，后续每次重建都带上。
- `scripts/verify-install.ps1`：新增 3 项卡门——`tools` 里有该脚本、脚本保留
  `dsh-auth` 选择器、`Launch.ps1` 带清理钩子；缺任何一项打包直接失败。
- 顺带修正 `FROZEN-BUILD.json` 两处陈旧元数据：`todoNudge` 1.0.0 → 1.3.0（rc.15 已升级
  但清单没改），`purgeRevert` 里「7 个冻结补丁脚本」→「11 个」。

- 本机故障现场的 71 个陈旧 cookie 已清理（原库备份在
